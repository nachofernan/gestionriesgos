# Actualizaciones — 26 de mayo de 2026

## Resumen

Implementación de un sistema de roles, estados unificados y flujo de aprobación para todas las entidades del módulo de auditoría (riesgo, control, objetivo, plan de acción, tarea). Incluye un historial de actualizaciones con validación por roles para proponer y aplicar cambios una vez que un elemento sale del estado borrador.

> **Revisión posterior (misma fecha):** se refinó el modelo completo de permisos y comportamiento de actualizaciones. Ver sección [Refinamiento del flujo](#refinamiento-del-flujo-de-actualizaciones) al final del documento.

---

## Roles de usuario

Se incorporó una columna `rol` en la tabla `users` (enum: `gerente`, `empleado`, `comite`, default `empleado`).

| Rol | Capacidad |
|---|---|
| `empleado` | Crea elementos (quedan en borrador) |
| `gerente` | Valida elementos en borrador; rechaza borradores |
| `comite` | Activa elementos validados |

El modelo `User` expone tres helpers: `esGerente()`, `esEmpleado()`, `esComite()`. El método `esGerente()` también devuelve `true` para usuarios sin área asignada (superusuarios), preservando el comportamiento anterior.

**Archivo:** `app/Models/User.php`  
**Seeder:** `database/seeders/RolSeeder.php` — asigna rol `gerente` al primer usuario sin área.

## Estados unificados

La tabla `estados_riesgo` fue renombrada a `estados`. Todos los modelos del módulo ahora referencian esta tabla mediante una FK `estado_id`.

### Tabla `estados`

| nombre | color | descripción |
|---|---|---|
| borrador | gray | Estado inicial al crear |
| validado | blue | Aprobado por gerente |
| activo | green | Activado por comité |
| borrado | red | Rechazado o eliminado |

### Modelos actualizados

- `Riesgo`, `Control`, `Objetivo`, `PlanAccion`, `Tarea`: campo `estado_id` en `$fillable`, relación `estado()` BelongsTo, y hook `booted()` que asigna automáticamente el estado `borrador` al crear.
- `Actualizacion`: ídem, con `estado_id` nullable.
- `EstadoRiesgo` mantenido como alias (`class EstadoRiesgo extends Estado`) para compatibilidad.

**Modelo principal:** `app/Models/Auditoria/Estado.php`  
**Migración:** `database/migrations/2026_05_26_000001_estados_unificados_y_roles.php`

## Flujo de aprobación por estado

### Transiciones válidas

```
[Empleado]  create()   →  borrador
[Gerente]   validar()  →  borrador   → validado
[Gerente]   rechazar() →  borrador   → borrado     (solo desde borrador)
[Comité]    activar()  →  validado   → activo
```

> **Importante:** un elemento validado no puede ser rechazado. `rechazar` solo aplica al estado `borrador`.

### Policies

Cada entidad tiene su Policy en `app/Policies/Auditoria/`. Los métodos `validar`, `activar` y `rechazar` verifican:
- Rol del usuario
- Área del usuario (hereda `puedeGestionarArea()`)
- Estado actual del elemento

**Ejemplo `RiesgoPolicy`:**
```php
public function validar(User $user, Riesgo $riesgo): bool
{
    return $user->esGerente()
        && $user->puedeGestionarArea($riesgo->area_id)
        && $riesgo->estado?->nombre === 'borrador';
}

public function rechazar(User $user, Riesgo $riesgo): bool
{
    return $user->esGerente()
        && $user->puedeGestionarArea($riesgo->area_id)
        && $riesgo->estado?->nombre === 'borrador';  // solo borrador
}
```

### Rutas agregadas

Para cada entidad (`riesgos`, `controles`, `objetivos`, `planes`, `tareas`):
```
POST /auditoria/{entidad}/{id}/validar
POST /auditoria/{entidad}/{id}/activar
POST /auditoria/{entidad}/{id}/rechazar
```

### Acciones en controllers

- `validar()`, `activar()`, `rechazar()`: cambian el `estado_id` del modelo y crean una **actualizacion activa** como log (sin flujo de aprobación).
- `edit()` y `update()`: redirigen al show con error si el elemento no está en borrador.

## Historial de actualizaciones

Todas las entidades tienen una relación polimórfica `actualizaciones()` (morphMany → tabla `actualizaciones`).

### Cuándo se crean actualizaciones

| Evento | Estado de la actualizacion |
|---|---|
| Creación del elemento (`store()`) | activo (log inmediato) |
| Transición de estado (validar/activar/rechazar) | activo (log inmediato) |
| Propuesta de cambio de campos (post-borrador) | borrador → flujo de aprobación |
| Propuesta de cambio de asociaciones (post-borrador) | borrador → flujo de aprobación |

### Regla clave: borrador vs. post-borrador

- **En borrador**: edición libre. El botón "Editar" es visible en el show y los paneles de gestión de relaciones permiten modificar directamente. No se generan actualizaciones de propuesta.
- **Fuera de borrador (validado / activo)**: el botón "Editar" desaparece. Cualquier cambio —campos o asociaciones— debe proponerse como una actualizacion y pasar por el flujo de aprobación antes de aplicarse al modelo.

### Flujo de aprobación de actualizaciones

```
[Cualquier usuario]  guardar propuesta  →  actualizacion en borrador
[Gerente]            validar()          →  actualizacion en validado
[Comité]             activar()          →  actualizacion en activo + cambios aplicados al modelo
[Gerente]            rechazar()         →  actualizacion en borrado
```

Al activar una actualizacion, los cambios se aplican en una transacción atómica:
```php
DB::transaction(function () use ($actualizacion) {
    $actualizacion->update(['estado_id' => Estado::activo()->id]);
    // campos escalares
    if (!empty($data['campos'])) {
        $model->update($data['campos']);
    }
    // relaciones M2M
    foreach ($data['relaciones'] as $rel => $ops) {
        if (isset($ops['sync'])) $model->$rel()->sync($ops['sync']);
        if (isset($ops['attach'])) $model->$rel()->attach($ops['attach']);
        if (isset($ops['detach'])) $model->$rel()->detach($ops['detach']);
    }
});
```

### Estructura del campo `data` (JSON)

```json
// Propuesta de campos escalares
{ "campos": { "nombre": "Nuevo nombre", "impacto": 8 } }

// Propuesta de cambio en asociaciones (ej. controles de un riesgo)
{ "relaciones": { "controles": { "sync": { "5": { "mitigacion": 3 }, "7": { "mitigacion": 5 } } } } }

// Log de creación (activo, sin aprobación)
{ "campos": { "nombre": "Riesgo X", "impacto": 7, "probabilidad": 6 } }
```

## Gestión de asociaciones post-borrador

Los componentes Livewire de gestión de relaciones (`GestionControles`, `GestionObjetivos`, `GestionPlanes`, `GestionTareas`) detectan si el modelo padre está en borrador mediante la propiedad `$esBorrador`.

| Estado | Botón mostrado | Acción al guardar |
|---|---|---|
| borrador | "Editar" (azul) | Sync directo |
| validado / activo | "Proponer cambio" (ámbar) | Crea actualizacion en borrador |

La propuesta codifica la intención en `data.relaciones` con la operación `sync` y los IDs resultantes. Al activarse, se aplica el sync completo al modelo padre.

## Refinamiento del flujo de actualizaciones

Esta sección documenta las correcciones y ampliaciones realizadas sobre el diseño inicial, que quedó operativo en la misma jornada.

---

### Matriz de estado de actualizacion por rol y estado del elemento

El estado con que nace una actualizacion depende de **quién** la crea y del **estado actual** del elemento padre. Los elementos en borrador no generan actualizaciones de propuesta; la edición es libre.

| Estado del elemento | empleado | gerente | comité |
|---|---|---|---|
| **borrador** | edición libre (sin actualizacion) | edición libre | — |
| **validado** | borrador | validado (se aplica de inmediato) | validado (se aplica de inmediato) |
| **activo** | borrador | validado | activo (se aplica de inmediato) |

> Gerente siempre genera `validado`. Comité genera su nivel máximo posible según el estado del elemento. Empleado siempre genera `borrador`.

---

### Campo `tipo` en el JSON `data`

Todas las actualizaciones ahora incluyen un campo `tipo` que permite distinguir logs de auditoría de propuestas de cambio aplicables:

| tipo | origen | ¿se aplica al activar? |
|---|---|---|
| `creacion` | `store()` al crear el elemento | No |
| `edicion` | `update()` mientras está en borrador | No |
| `validacion` | `validar()` del elemento | No |
| `activacion` | `activar()` del elemento | No |
| `rechazo` | `rechazar()` del elemento | No |
| `cambio` | propuesta post-borrador (Gestión components o GestionActualizaciones) | Sí |

`aplicarCambiosActualizacion()` y `aplicarCambios()` saltan cualquier actualizacion cuyo `tipo` no sea `cambio` (o sin `tipo`, por compatibilidad con registros previos).

---

### Historial desde la creación

- **`store()`** en los 5 controllers crea una actualizacion con `tipo=creacion` en estado **borrador**, capturando todos los campos del elemento.
- **`update()`** en borrador captura los campos modificados (comparando `$original` vs nuevo) y crea una actualizacion `tipo=edicion` con diff `{antes, despues}` por campo.
- El componente `GestionActualizaciones` se muestra **siempre** en el show (incluso en borrador), pero el botón "Nueva Actualización" solo aparece cuando el elemento no está en borrador.

---

### `validar()` del elemento: sellado en cadena

Al validar un elemento:
1. Todas las actualizaciones del elemento en estado `borrador` pasan en bloque a `validado` (bulk update).
2. Se crea un log `tipo=validacion` en estado `validado`.

Ya no se genera un snapshot completo en el log de validación; la historia completa está en los registros `creacion` y `edicion` previos.

---

### Aplicación inmediata en elemento validado

Cuando el elemento está en `validado`, las propuestas de gerente o comité (que nacen como `validado`) **se aplican inmediatamente** al modelo, sin esperar a que el comité active el elemento.

Esto aplica en:
- Todos los Gestión components (`guardar()` con `aplicarAhora = estadoId === validado && estadoModelo === validado`)
- `GestionActualizaciones.guardar()` (ídem)
- `GestionActualizaciones.validarActualizacion()`: si el elemento padre está en `validado`, llama `aplicarCambiosDesdeActualizacion()` tras cambiar el estado
- `ActualizacionController.validar()`: mismo chequeo sobre el padre vía `actualizable`

---

### Estructura extendida del campo `data` (diff)

Las propuestas de `tipo=cambio` incluyen una sección `diff` para mostrar qué cambia exactamente:

```json
// Propuesta de campo escalar con diff
{
  "tipo": "cambio",
  "campos": { "nombre": "Nuevo nombre" },
  "diff": {
    "campos": {
      "nombre": { "antes": "Nombre viejo", "despues": "Nuevo nombre" }
    }
  }
}

// Propuesta de relación con diff
{
  "tipo": "cambio",
  "relaciones": { "controles": { "sync": { "3": { "mitigacion": 5 } } } },
  "diff": {
    "relaciones": {
      "controles": {
        "agrega": [{ "id": 3, "nombre": "Control C", "mitigacion": 5 }],
        "quita":  [{ "id": 1, "nombre": "Control A" }],
        "cambia": [{ "id": 2, "nombre": "Control B", "mitigacion_antes": 3, "mitigacion_despues": 7 }]
      }
    }
  }
}

// Log de creación
{
  "tipo": "creacion",
  "campos": { "nombre": "Riesgo X", "impacto": 7, "probabilidad": 6, ... }
}

// Log de edición en borrador
{
  "tipo": "edicion",
  "diff": { "campos": { "impacto": { "antes": 6, "despues": 7 } } }
}
```

### Visibilidad de botones de acción en actualizaciones

| Estado del elemento | Validar | Activar | Rechazar | Cancelar |
|---|---|---|---|---|
| borrador | No | No | No | Sí (solo el creador, mientras borrador) |
| validado | Sí (gerente, en propuestas borrador) | No | Sí (gerente) | Sí (creador) |
| activo | Sí (gerente) | Sí (comité) | Sí (gerente) | Sí (creador) |

- **Activar individual**: solo en elemento `activo` (en `validado`, la activación ocurre al activar el elemento completo).
- **Cancelar**: el propio creador puede retirar su propuesta mientras esté en `borrador`. Policy: `user_id === actualizacion.user_id && estado === borrador`.
