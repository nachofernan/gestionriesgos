# Actualizaciones — 27 de mayo de 2026

## Resumen

Implementación del sistema de visibilidad jerárquica por rol y estado para todas las entidades del módulo de auditoría. Los elementos activos son visibles para todos; los validados y borradores siguen reglas estrictas según el rol y la posición del usuario en el árbol de áreas. Incluye tests automáticos completos y corrección de una brecha de seguridad en la creación de riesgos y planes de acción.

---

## Reglas de visibilidad

La visibilidad de un elemento depende de su estado y del rol del usuario que consulta:

| Estado | Comité | Gerente | Empleado |
|---|---|---|---|
| `activo` | Todos | Todos | Todos |
| `validado` | Todos | Solo en su gerencia + sub-áreas | Solo en toda su gerencia (sube hasta nivel 1) |
| `borrador` | Ninguno | Solo en su gerencia + sub-áreas | Solo en su propio sector + sub-áreas |
| `borrado` | Ninguno | Solo en su gerencia + sub-áreas | Solo en su propio sector + sub-áreas |

**"Gerencia"** = área de nivel 1 (hijo directo del área raíz del comité). Un empleado en "Desarrollo" → su gerencia es "Gerencia Administración". Un empleado puede ver borradores de su sector, pero **no** de sectores hermanos dentro de la misma gerencia.

## Area model: `obtenerIdsSubarbol()`

**Archivo:** `app/Models/Auditoria/Area.php`

Nuevo método que recorre recursivamente el árbol desde un área hacia abajo y devuelve todos los IDs del subárbol (incluyendo la propia área).

```php
public function obtenerIdsSubarbol(): array
{
    $ids = [$this->id];
    foreach ($this->hijos as $hijo) {
        $ids = array_merge($ids, $hijo->obtenerIdsSubarbol());
    }
    return $ids;
}
```

Reemplaza el método privado `obtenerAreasHijas()` que estaba duplicado en cada componente Search de Livewire.

## User model: nuevos helpers de visibilidad

**Archivo:** `app/Models/User.php`

### `areaGerencia(): ?Area`

Sube por el árbol de áreas hasta encontrar el área cuyo padre es la raíz (área sin `area_padre_id`). Esa área es la "gerencia" del usuario, independientemente de cuántos niveles haya entre el usuario y la raíz.

```php
public function areaGerencia(): ?Area
{
    if (!$this->area_id) return null;
    $area = $this->area;
    while ($area && $area->area_padre_id !== null) {
        $padre = Area::find($area->area_padre_id);
        if ($padre?->area_padre_id === null) return $area;
        $area = $padre;
    }
    return $area;
}
```

### `puedeVerEnGerencia(mixed $areaId): bool`

Verifica si un área dada pertenece a la gerencia completa del usuario. Usada para validar visibilidad de elementos `validado` para empleados.

```php
public function puedeVerEnGerencia(mixed $areaId): bool
{
    if (!$this->area_id || !$areaId) return true;
    $gerencia = $this->areaGerencia();
    return $gerencia?->esAncestroOIgual((int) $areaId) ?? false;
}
```

## Trait `HasVisibilityScope`

**Archivo nuevo:** `app/Models/Concerns/HasVisibilityScope.php`

Trait que implementa `scopeVisiblePara(Builder $query, User $user)`. Se aplica a los 5 modelos del módulo mediante `use HasVisibilityScope`.

```php
public function scopeVisiblePara(Builder $query, User $user): Builder
{
    if (!$user->area_id) return $query; // super-admin sin área: ve todo

    $activoId   = Estado::activo()?->id;
    $validadoId = Estado::validado()?->id;

    if ($user->esComite()) {
        return $query->whereIn('estado_id', array_filter([$activoId, $validadoId]));
    }

    $propiaIds = $user->area->obtenerIdsSubarbol();

    if ($user->esGerente()) {
        return $query->where(fn($q) =>
            $q->where('estado_id', $activoId)
              ->orWhereIn('area_id', $propiaIds)
        );
    }

    // Empleado
    $gerencia    = $user->areaGerencia();
    $gerenciaIds = $gerencia ? $gerencia->obtenerIdsSubarbol() : $propiaIds;

    return $query->where(fn($q) =>
        $q->where('estado_id', $activoId)
          ->orWhere(fn($q2) => $q2->where('estado_id', $validadoId)->whereIn('area_id', $gerenciaIds))
          ->orWhere(fn($q2) => $q2->whereNotIn('estado_id', array_filter([$activoId, $validadoId]))->whereIn('area_id', $propiaIds))
    );
}
```

El scope se compone correctamente con otros filtros (búsqueda, área, estado) aplicados posteriormente en los componentes Search.

## Policies: método `view()`

**Archivos:** los 5 en `app/Policies/Auditoria/`

Agregado `view()` a cada policy para proteger el acceso directo por URL a elementos que el usuario no tiene permitido ver. Los controllers invocan `$this->authorize('view', $model)` en `show()`.

```php
// Ejemplo en RiesgoPolicy
public function view(User $user, Riesgo $riesgo): bool
{
    $estado = $riesgo->estado?->nombre;
    if ($estado === 'activo') return true;
    if (!$user->area_id) return true; // super-admin

    if ($user->esComite()) return $estado === 'validado';
    if ($user->esGerente()) return $user->puedeGestionarArea($riesgo->area_id);

    // Empleado
    if ($estado === 'validado') return $user->puedeVerEnGerencia($riesgo->area_id);
    return $user->puedeGestionarArea($riesgo->area_id); // borrador/borrado
}
```

## Corrección de seguridad: formularios de creación y edición

### Problema identificado

Al crear un riesgo (`RiesgoController::create()`), el formulario mostraba **todos** los objetivos sin filtro de visibilidad. Además, la validación en `store()` y `asociarObjetivos()` solo verificaba que el ID existiera (`exists:objetivos,id`), sin comprobar si el usuario tenía acceso al objetivo. Un empleado podía asociar objetivos de otras gerencias manipulando el POST directamente.

Lo mismo ocurría en `PlanAccionController`: los formularios `create()` y `edit()` mostraban todos los riesgos, y `store()` / `update()` no validaban visibilidad.

### Corrección aplicada

**`RiesgoController`:**
- `create()`: `$objetivos` filtrado con `->visiblePara(Auth::user())`.
- `store()` y `asociarObjetivos()`: validación de `objetivos.*` usa `Rule::in(Objetivo::visiblePara(...)->pluck('id'))` además de `exists`.

**`PlanAccionController`:**
- `create()` y `edit()`: `$riesgos` filtrado con `->visiblePara(Auth::user())`.
- `store()` y `update()`: validación de `riesgo_ids.*` usa `Rule::in(Riesgo::visiblePara(...)->pluck('id'))`.

Ambos controllers importan ahora `use Illuminate\Validation\Rule;`.

## Modal de validación en cascada (Bulk Validation)

Al hacer clic en **Validar** o **Activar** sobre una entidad completa (no una actualización), el sistema intercepta la acción y abre un modal que analiza las dependencias jerárquicas, las presenta con checkboxes y ejecuta la validación en el orden correcto.

Aplica a **ambos pasos** de transición: `borrador → validado` y `validado → activo`.

---

### Jerarquía de dependencias

```
Objetivo ←→ Riesgo ←→ Control (independiente, sin prerequisito)
              ↓
          PlanAccion ←→ Tarea
```

**Reglas de bloqueo (prerequisitos):**

| Entidad | Acción | Prerequisito |
|---|---|---|
| Riesgo | validar | Al menos 1 Objetivo debe ser `validado` o `activo` |
| Riesgo | activar | Al menos 1 Objetivo debe ser `activo` |
| PlanAccion | validar | Al menos 1 Riesgo debe ser `validado` o `activo` (recursivo: si el Riesgo tampoco tiene Objetivo validado, también lo muestra) |
| PlanAccion | activar | Al menos 1 Riesgo debe ser `activo` |
| Objetivo / Control / Tarea | cualquiera | Sin prerequisitos |

**Opcionales en cascada (hijos):**

| Entidad | Validar ofrece | Activar ofrece |
|---|---|---|
| Riesgo | Controles en `borrador` | Controles en `validado` |
| PlanAccion | Tareas en `borrador` | Tareas en `validado` |

---

### Flujo del modal

1. Usuario hace clic en **Validar** o **Activar** → se dispara `Livewire.dispatch('abrir-validacion-cascada', {...})`
2. El componente `ValidacionCascadaModal` recibe el evento, carga la entidad y llama a `ValidacionMasivaService::analizar()`
3. El modal muestra:
   - **Prerequisitos requeridos** (fondo amber): ítems que deben validarse primero. Al menos uno debe quedar seleccionado. Ítems sin permisos aparecen grises y no son seleccionables.
   - **Opcionales** (sin fondo): ítems que pueden incluirse en el bulk. Los no seleccionados quedan en su estado actual.
   - **Orden de ejecución**: lista numerada con el orden en que se procesarán los ítems seleccionados.
   - Si no hay dependencias: confirmación simple de una línea.
4. Al confirmar, el servicio procesa en orden: prerequisitos (nivel mayor primero) → opcionales → entidad principal.
5. Si un prerequisito falla (sin permisos o error DB), se hace rollback total. Si falla un opcional, se omite y el resto continúa.

### `ValidacionMasivaService`

**Archivo:** `app/Services/Auditoria/ValidacionMasivaService.php`

```php
public function analizar(Model $entidad, string $accion, User $usuario): array
// Retorna: ['bloqueantes' => [...], 'opcionales' => [...]]
// Cada ítem: ['tipo', 'id', 'nombre', 'estado', 'puede_validar', 'nivel', 'parent_tipo', 'parent_id']

public function ejecutar(Model $entidad, string $accion, array $bloqueantesSeleccionados, array $opcionalesSeleccionados, User $usuario): array
// Retorna: ['ok' => true, 'exitosos' => [...], 'fallidos' => [...]]
//       o: ['error' => '...', 'fallidos' => [...]]
```

El método `procesarTransicion()` replica exactamente la lógica de los controllers existentes (`validar()` aplica la transición borrador→validado con log; `activar()` aplica cambios pendientes de actualizaciones y transiciona a activo). El método `aplicarCambiosActualizacion()` es una copia de los controllers para mantener consistencia.

Toda la ejecución ocurre dentro de `DB::beginTransaction()` / `DB::commit()`. Si un bloqueante falla → `DB::rollBack()`. Si solo fallan opcionales → se commitea lo que pudo procesarse.

### `ValidacionCascadaModal` (Livewire)

**Archivo:** `app/Livewire/Auditoria/ValidacionCascadaModal.php`

Componente genérico incluido en todos los show pages. Arranca dormido (`$abierto = false`) y se activa al recibir el evento `abrir-validacion-cascada`.

Propiedades públicas clave: `$tipo`, `$entidadId`, `$accion`, `$nombre`, `$bloqueantes[]`, `$opcionales[]`, `$seleccionados[]` (key: `'tipo:id'`), `$error`.

Métodos:
- `abrir(string $tipo, int $id, string $accion)` — listener `#[On('abrir-validacion-cascada')]`; verifica Gate sobre la entidad principal antes de abrir
- `toggleSeleccion(string $tipoId)` — flip de checkbox con validación de mínimo 1 bloqueante seleccionado
- `confirmar()` — valida selección, llama al servicio, redirige con flash en éxito o muestra error inline
- `cancelar()` — hace `$this->reset()`
- `resumen(): array` — lista ordenada para el UI (bloqueantes desc por nivel, luego opcionales, luego principal)
