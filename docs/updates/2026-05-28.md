# Actualizaciones — 28 de mayo de 2026

## Resumen

Corrección de una brecha de autorización en el sistema de actualizaciones (propuestas de cambio): cualquier gerente podía validar o rechazar propuestas sobre elementos de otras gerencias. Se restringió la policy para que solo el gerente del área responsable del elemento pueda operar sobre sus actualizaciones. Además se cerró un hueco equivalente en el componente Livewire `GestionActualizaciones`. Se acompaña con 23 tests automáticos.

---

## Problema corregido

### `ActualizacionPolicy` sin restricción de área

Los métodos `validar()` y `rechazar()` solo verificaban que el usuario fuera gerente y que la actualización estuviera en estado `borrador`, pero no comprobaban si el gerente tenía permisos sobre el área del elemento al que pertenecía la actualización.

Ejemplo del escenario roto: el gerente de producción podía validar una propuesta de cambio sobre un objetivo de la gerencia de administración.

```php
// ANTES — cualquier gerente pasaba
public function validar(User $user, Actualizacion $actualizacion): bool
{
    return $user->esGerente()
        && $actualizacion->estado?->nombre === 'borrador';
}
```

### `GestionActualizaciones::guardar()` sin autorización

El método del componente Livewire creaba actualizaciones sin verificar permisos sobre el elemento padre. El `ActualizacionController` (vía HTTP) sí lo hacía con `$this->authorize('update', $entity)`, pero el componente Livewire no tenía esa verificación.

---

## Cambios implementados

### `app/Policies/Auditoria/ActualizacionPolicy.php`

Se agrega `puedeGestionarArea()` en `validar()` y `rechazar()`, obteniendo el `area_id` del elemento padre (`actualizable`) a través de la relación polimórfica:

```php
public function validar(User $user, Actualizacion $actualizacion): bool
{
    $areaId = $actualizacion->actualizable?->area_id;
    return $user->esGerente()
        && $user->puedeGestionarArea($areaId)
        && $actualizacion->estado?->nombre === 'borrador';
}

public function rechazar(User $user, Actualizacion $actualizacion): bool
{
    $areaId = $actualizacion->actualizable?->area_id;
    return $user->esGerente()
        && $user->puedeGestionarArea($areaId)
        && $actualizacion->estado?->nombre === 'borrador';
}
```

El método `activar()` (comité) no se modificó: el comité tiene `area_id = null`, lo que hace que `puedeGestionarArea()` retorne `true` para cualquier área. Comportamiento correcto y sin cambios necesarios.

### `app/Livewire/Auditoria/Actualizaciones/GestionActualizaciones.php`

Se agrega `$this->authorize('update', $model)` al inicio de `guardar()`, antes de procesar los datos del formulario:

```php
public function guardar(): void
{
    $this->validate(['mensaje' => 'required|string|min:3']);

    $model    = $this->resolverModelo();
    $this->authorize('update', $model);   // ← agregado
    $estadoId = $this->estadoParaActualizacion();
    // ...
}
```

## Tests automáticos

**Archivo nuevo:** `tests/Feature/Auditoria/ActualizacionPermisoTest.php`

23 tests que cubren todos los escenarios de permisos sobre actualizaciones. La suite es autónoma y usa la misma jerarquía de áreas y usuarios que `VisibilidadTest`.

### Jerarquía de prueba

```
comite (raíz)
├── gerAdmin   ← canela (gerente)
│   ├── sectA  ← nacho  (empleado)
│   └── sectB  ← tito   (empleado, hermano de nacho)
└── gerProd    ← grassi (gerente)
    └── sectC  ← nocetti (empleado)
```

### Grupos de tests

| Grupo | Tests | Qué verifica |
|---|---|---|
| Policy `validar` | 6 | Gerente puede validar en su gerencia y sub-áreas; no puede en gerencia ajena; requiere estado borrador; empleado bloqueado |
| Policy `rechazar` | 3 | Gerente puede rechazar en su gerencia; no en gerencia ajena; requiere estado borrador |
| Policy `activar` | 2 | Comité puede activar en cualquier gerencia; requiere estado validado |
| Policy `cancelar` | 3 | Autor puede cancelar la propia en borrador; otro usuario no puede; requiere estado borrador |
| HTTP `validar` | 3 | 403 para gerente de otra gerencia; redirect para gerente correcto; 403 para empleado |
| HTTP `rechazar` | 2 | 403 para gerente de otra gerencia; redirect para gerente correcto |
| HTTP `store` | 4 | 403 si el usuario no gestiona el área del elemento; redirect si tiene permisos; empleado bloqueado fuera de su área |
